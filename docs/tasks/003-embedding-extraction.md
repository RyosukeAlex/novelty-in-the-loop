# Task 003: 埋め込みの取り出し方針

**担当：りけ（実装）／ Claude（方針・レビュー）**
方針確定日：2026-10-24

## 目的

GCS の SPECTER2 埋め込み（1.62TiB）から、パイロットに必要な **499,727 本**分だけを抜き出し、
`paperid → 768次元ベクトル` の形で手元に持つ。

対象の内訳は `docs/pilot.md`（2026-10-24 の節）を参照。
`pilot_neighbors` の `has_text = TRUE` がそのリストになる。

---

## 1. 調査でわかった事実（2026-10-24 実測）

### ファイル構成

| 項目 | 値 |
|---|---|
| 置き場所 | `gs://sciscinet-neo/v2/embeddings/sciscinet_emb_chunk_0000.jsonl` 〜 `_0111.jsonl` |
| ファイル数 | 112 |
| 合計 | 1,783,495,926,750 bytes（1.62TiB） |
| 1ファイル | 16,10x,xxx,xxx bytes（約 16.1GB）。最後の `_0111` のみ 14.2GB |
| **1ファイルの行数** | **ちょうど 1,000,000 行**（2026-10-25 実測。当初 2^20 = 1,048,576 行と推定したが誤り） |
| **1行の平均サイズ** | **約 15.7 KB**（16,103 bytes） |
| 全体の行数 | **約 1.119 億行**（111 × 100万 + 最後のファイル約 88 万行） |
| 1行の形式 | `{"paperid": "W574406607", "embedding": [0.037212..., ...]}` |
| 次元 | 768（L2 正規化されていない。ノルム約 21.5） |

### 埋め込みは「テキストがある論文」にほぼ一致して存在する

行数 **約 1.119 億**に対し、`sciscinet_papertitleabstract` は **1.2235 億行**（差 9%）。
`sciscinet_papers` は 2.498 億行なので、**全論文の約半分にしか埋め込みがない**。

> これは `pilot_neighbors.has_text` で絞る設計の裏付けになる。
> テキストがない論文は埋め込みも存在しないと考えてよい（走査時に実測して確認する）。

### 🚨 `paperid` のソートは当てにできない

先頭だけ見ると昇順に見えるが（chunk_0000 → 0050 → 0111 で単調増加）、**全112ファイルの
先頭/末尾を実測すると崩れている**（`data/explore/embedding_chunk_ranges.csv`）。

| 検査 | 結果 |
|---|---|
| ファイル境界が連続（前の末尾 < 次の先頭） | **109 / 111** |
| ファイル内が昇順（先頭 < 末尾） | **60 / 112** |

ファイル境界はほぼ連続しているのに、ファイル内の昇順は半分しか成立しない。
つまり全体は1本の列だが、**約52箇所で ID が巻き戻る**（並列エクスポートされた
ソート済みセグメントを順に連結した構造）。

> **帰結：二分探索もファイルスキップも使えない。112 ファイルすべてを 1 行ずつ走査するしかない。**
> 「ソート済みだから必要な部分だけ読める」という近道は存在しない。

### 実測値（2026-10-25、1 ファイル目）

| 項目 | 実測 |
|---|---|
| 走査速度 | **4,513 行/秒**（約 73 MB/s）。**CPU 律速**（GCS は 145 MB/s 出る） |
| 1 ファイルの所要 | 221.6 秒（並列 1） |
| 111 ファイルの推定 | 8 並列で**約 51 分** |
| バケットの読み出し速度 | **145 MB/s**（自分の US マルチリージョンは 173.6 MB/s） |

> **リージョンのリスク判定：** 速度が US バケットと同程度なので **US 内**と判断した。
> 別大陸なら数十 MB/s に落ちる。最悪ケース（$190〜220）は排除され、
> 想定コストは **$0（US マルチリージョン）〜 $17（US 内別リージョン）**。
> 課金レポートは反映に数時間〜1 日かかるため、速度による間接判定を採用した。

> **ヒットはファイルによって極端に偏る。** `chunk_0000`（ID 範囲 W574406607〜W2273250747 ＝
> 古い論文）のヒットは **3 件のみ**。対象は ML 2016–2018 とその近傍で ID が大きいため、
> 後半のファイルに集中する。**全体のヒット数は変わらないので、全走査の必要性は変わらない。**

## 2. 方針

### 全走査する。同一リージョンの VM から 1 回だけ。

1. 対象 `paperid` のリスト（499,727 件）を BigQuery から CSV でエクスポートし、VM で `set` に読み込む
2. 112 ファイルを GCS からストリーミング読み出しし、**1行ごとに `paperid` だけを文字列で判定**する
3. ヒットした行（0.4%）のみ JSON をパースし、ベクトルを保存
4. 結果を `float32` の `.npy` と `paperid` の順序リストにして自分のバケットへ置き、手元に落とす

### 速度の鍵：JSON をパースしないこと

ヒット率は 499,727 / 1.119億 = **0.447%**。残り 99.55% の行は捨てる。
1行 15KB を JSON パースすると 768 個の float 変換が走り、全体で数十時間かかる。

**行の先頭 30 バイトに `{"paperid": "W574406607",` があるので、そこだけ見て判定する。**
ヒットした行だけパースすれば、パース回数は 1.173億 → 50万回に落ちる。

### 却下した案

| 案 | 却下理由 |
|---|---|
| BigQuery の外部テーブルで JSON を読む | 列を選んでも JSON 全体を読むため 1.78TB スキャン。月の無料枠（1TB）の 1.8 倍 |
| ローカルに全ダウンロード | インターネット egress 1.62TiB ≒ **$200 規模** |
| `paperid` の二分探索で必要な行だけ range read | **ソートが崩れているため不可**（§1） |
| Dataflow / Dataproc | 1 回しか実行しない処理に対して設定コストが過大 |

## 3. コスト見積もり

| 項目 | 見積もり |
|---|---|
| GCS → 同一リージョン VM の読み出し | **$0**（同一ロケーション内は egress 無料） |
| VM（`e2-standard-8`、8 vCPU / 32GB、2 時間想定） | オンデマンド $0.54 / Spot $0.16 |
| ディスク（50GB、2 時間） | 約 $0.01 |
| GCS Class B 操作（112 ファイル分の GET） | 約 $0 |
| 成果物（約 1.5GB）のローカルへのダウンロード | 約 $0.18 |
| **合計** | **$1 未満** |

出力サイズ：499,727 × 768 × 4 bytes(float32) = **1.53 GB**。手元で扱える。

### ⚠️ 未解決のリスク：バケットのリージョンが確認できない

`gcloud storage buckets describe gs://sciscinet-neo` は **権限エラー**（`storage.buckets.get` が無い）。
提供元の BigQuery データセット `ksm-rch-scisciturbo.sciscinet_v2` が US なので
バケットも US と推測できるが、**確認できていない**。

リージョンが違うと egress が課金され、**1.62TiB で $190〜220** になる。

> **対策：`us-central1` に VM を立て、まず 1 ファイル（16GB）だけ処理して課金レポートを確認する。**
> 最悪でも 16GB 分の誤課金（約 $2）で止まる。無料と確認できてから残り 111 ファイルを流す。

## 4. 手順

### 4-1. 対象リストのエクスポート（BigQuery、無料）

`pilot_neighbors` の `has_text = TRUE` を GCS へ CSV エクスポートする。
中間テーブルは小さいのでスキャンは無視できる。自分のバケット（US）が必要。

### 4-2. VM の用意

- リージョン：**`us-central1`**（バケットが US マルチリージョンなら egress 無料）
- マシン：`e2-standard-8`。Spot インスタンスで十分（中断しても再開できる設計にする）
- スコープ：GCS の読み取りと自分のバケットへの書き込み

### 4-3. 走査スクリプト（りけが実装）

使うもの：

- `google-cloud-storage` の `blob.open("rt")` — ストリーミング読み出し。
  行の途中で切れる心配がない（`gcloud storage cat -r` でバイト範囲を指定する方式とは違う）
- `orjson` — ヒットした行のパースに使う。標準 `json` より数倍速い
- `numpy` — 出力を `float32` の配列にする
- `multiprocessing` — ファイル単位で 8 並列

骨格：

```
対象セット = CSV から paperid を読んで set にする    # 約25MB

各ファイルについて（8並列、ファイル単位）:
    出力用のリスト = []
    blob を "rt" で開いて 1 行ずつ:
        先頭30バイトから paperid を切り出す          # ここが速度の鍵
        対象セットに無ければ次の行へ
        あれば orjson でパースして embedding を取る
        リストに (paperid, vector) を追加
    そのファイル分を .npy と paperid リストで保存    # 中断に備えて逐次保存

全ファイル分をマージ → 1つの .npy + paperid の順序リスト
```

### 4-4. 検証（走査後に必ず）

- [ ] 取れた件数と 499,727 の差を確認する。**取れなかった論文のリストを残す**
- [ ] 取れなかった論文が `pilot_neighbors` のどの層（①対象 / ②参考文献 / ③被引用）に
      偏っていないか確認する。偏っていれば過去/未来ベクトルの品質に影響する
- [ ] ベクトルのノルムが約 21.5 であることを数本で確認する（取り違えの検出）
- [ ] 走査した総行数が約 1.173 億であることを確認する（§1 の推定の検証）

## 5. 落とし穴

- **`paperid` の切り出しを固定オフセットでやらない。** ID は `W574406607`（10桁）から
  `W4394281656`（11桁）まで桁数が違う。`"paperid": "` の後ろから次の `"` までを取る
- **ヒットした行だけパースする**（§2）。全行パースすると桁違いに遅くなる
- **逐次保存する。** Spot インスタンスは中断される。112 ファイルを 1 つのトランザクションに
  しない。ファイル単位で保存し、再開時は未処理のファイルだけ流す
- **1 ファイル目で止めて課金を確認する**（§3 のリスク）
- **VM は使い捨てにする。** 設定を積み上げない（`docs/handover.md` §4 の方針）

## 6. この後に続くもの

走査が終われば、`docs/pilot.md` の検証①②に進める。

- 過去ベクトル＝参考文献の埋め込み平均（`year_diff >= 0` のエッジのみ使う。リーク対策）
- 未来ベクトル＝被引用論文の埋め込み平均（5年窓）
- 散らばり系の特徴量（分散・最大ペア間距離・クラスタ数）も同時に算出する（池田先生の指摘）

生じたときに着手すればよく、パイロットの前提ではない。
