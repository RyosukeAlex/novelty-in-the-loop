## 1. 研究の全体像

**テーマ（案）:** 科学的新規性の事前評価と、その組み込み位置
― 内容埋め込みに基づく新規性指標による研究エージェントの改善 ―

**一文:** 非類似度に頼る AI の新規性判定を、引用構造に基づく「動き」としての新規性で置き換え、その改善効果と原理的な限界を明らかにし、さらにその評価器をエージェント系のどこに置くと最も効くかを比較する。

### 新規性の三分割（理論的土台）

| | 名称 | 測定対象 | 確定時点 |
|---|---|---|---|
| ① | 材料の新規性 | 参考文献の組み合わせの異例さ | 出版時 |
| ② | 内容の新規性 | 既存知識空間からの意味的距離 | 出版時 |
| ③ | 効果の新規性 | 分野の進み方を変えたか | **出版後** |

③は社会的に構成されるため、事前評価は定義上不可能。既存指標間の相関がほぼゼロなのは、これらが別の構成概念を測っているため。

### 章構成（5章）

| 章 | 内容 | 役割 |
|---|---|---|
| 第1章 | 問題設定：非類似度 ≠ 新規性 | 動機 |
| 第2章 | 事後の新規性指標の構築 | 正解ラベルを作る |
| 第3章 | 事前予測器と予測上限の測定 | 組み込む部品を作る |
| 第4章 | AI Scientist への組み込みと評価（A/B/C 3条件） | **主役** |
| 第5章 | 組み込み位置の比較（P1生成時 / P2選択時 / P3査読時） | 配置の設計指針 |

各章は独立に成立するよう設計。後の章が頓挫しても前の章だけで論文になる。

### ボトルネック

成否条件②「テキストから、非類似度（B）を超えて『動き』を予測できるか」。
**これが通らなければ第4章・第5章の土台がない。** したがって Step 1.5 のパイロットで最初に検証する。

## 3. データ上の前提（LimSight Step 1 からの引き継ぎ）

同一データセットのため、以下はすべて本研究にも適用される。

### 3-1. disruption = 0 は信用できない

`disruption` に NULL はなく、**73.9%（1.79億本）が 0**。うち 85.4% が参考文献0件。参考文献0件の論文は、定義上 D=1 になるべきもの（被引用あり・3,204万件）と計算不能なもの（被引用なし・1.28億件）の両方が、すべて 0 で格納されている。

D の値域は -1〜+1 で 0 は「中立」という実在の値なので、これは欠損処理ではなく**系統的な下方バイアス**。

**対応:** `WHERE reference_count > 0 AND citation_count > 0` で除外する。補正はしない。

**本研究での意味:** D-index は第2章のベースラインであり目的変数ではないため、一度算出すれば済む。むしろこの発見自体が論拠に使える ――「既存の破壊性指標は参考文献・被引用が両側に必要で、適用範囲が構造的に制約される」。これは提案手法（内容ベース）の動機づけを強める。

### 3-2. C3/C5/C10 は新しい年で窓が閉じていない

NULL は0件、累積性も確認済みなので 0 は「引用なし」で正しい。ただしデータが実質2024年までのため、新しい論文では窓が埋まらない。

**窓が閉じている年の目安: C3 → 2021年まで / C5 → 2019年まで / C10 → 2014年まで。**

**本研究での意味:** 第2章の「動き」指標も第3章の目的変数も引用窓に依存する。パイロットの5年窓（2012〜2014年対象）は C5 の範囲内で安全。

### 3-3. cited_by_count と citation_count の使い分け

- `cited_by_count` = OpenAlex のグローバル被引用数（コーパス外を含む）
- `citation_count` = SciSciNet コーパス内で再計算した値
- 一致 89.7%、`cited_by_count >` が 9.7%、`<` が 0.6%

**引用ネットワーク解析（過去/未来ベクトル、D-index）は `paperrefs` と整合する `citation_count` を使う。**

### 3-4. 【要修正】score_openalex の閾値 — ML は特殊

`sciscinet_paperfields.score_openalex` の分布は分野によって大きく違う。

| 分野 | p50 | >= 0.5 の割合 |
|---|---:|---:|
| Computer science (L0) | 0.333 | 17.9% |
| Artificial intelligence | 0.202 | 14.1% |
| **Machine learning** | **0.056** | **6.8%** |
| Computer vision | 0.376 | 25.1% |
| Natural language processing | 0.397 | 23.0% |

**ML だけが一桁低い外れ値。** 階層レベルの交絡ではない（L0 の CS と L1 の多数分野がほぼ同水準）。また中央値と通過率が連動しないため、分野ごとに裾の広がりが違う。

> **既存クエリの修正が必要:** `sql/explore/03_pilot_target_count.sql` および `04_pilot_neighbor_count.sql` は `score_openalex >= 0.5` を使っている。ML ではこれが 6.8% しか通さず、対象が不当に狭まる。**固定閾値をやめ、分位点ベース（その分野の p90 等）に変えるか、閾値決定を先に行う。**

**仮説（未検証）:** ML の低スコア側の長い裾は「ML を道具として使っただけの応用論文」である可能性。正しければ、パイロットのコーパス構築で ML には厳しい絞り込みが必要という根拠になる。

### 3-5. その他

- **スナップショット終端:** `MAX(date)` = 2025-12-31 だが 2025年は869本のみ。**`year <= 2024` で絞る**
- **doctype:** 8種・NULL なし。対象は `article` + `preprint`（arXiv 版を含めるかは設計判断）
- **撤回論文:** 50,101件。`is_retracted` で区別。指標算出では除外するか明示的に設計する
- **is_paratext:** 全件 false ＝ v2 では機能していない列
- **Atyp_Median_Z / Atyp_10pct_Z:** `disruption` と違い欠損を NULL で正しく表現（75.5%）。**同じテーブル内で欠損の表現が統一されていないため、カラムごとに確認が必要**
- **Atyp_Pairs = 0:** NULL とは別の意味（ペアが取れなかった）

## 4. 開発環境

### 構成

| 用途 | 環境 |
|---|---|
| 開発 | Mac + VS Code + Claude Code（サブスクで利用、API課金なし） |
| データ | GCP（BigQuery `ksm-rch-scisciturbo.sciscinet_v2`、US リージョン） |
| 埋め込み走査 | 使い捨ての VM（US リージョン）を一度だけ立てる想定 |
| コード管理 | GitHub `RyosukeAlex/novelty-in-the-loop`（HTTPS + PAT） |

**クラウド上の IDE は使わない。** Vertex AI Workbench を試したが、ブラウザのない環境での認証（gh / Claude Code）で手間が増えるだけだった。GCP は「データのある場所」であって開発の常駐先ではない。VM は使い捨てにし、設定を積み上げない。

### bq の落とし穴

- **テーブルは非パーティション。** `WHERE` や `LIMIT` ではスキャン量が減らない（`LIMIT 100` でも 11.2GB）。減らせるのは**選ぶ列の数だけ**
- **本番クエリの前に必ず `--dry_run`**
- 同一クエリの24時間以内の再実行はキャッシュで課金0
- 中身を覗くだけなら `bq head -n 10 <table>`
- **SQL ファイルを `"$(cat ...)"` で渡すと、先頭の `--` コメントがフラグと解釈されて失敗する。** 標準入力から渡すこと:
  ```bash
  bq query --use_legacy_sql=false --format=csv < sql/explore/xx.sql > data/explore/xx.csv
  ```
- `--max_rows` を指定しないと100行で切れる

### API 課金が必要になる地点

第4章以降の AI Scientist 実行時のみ。サブスクでは代替できない（プログラムからの LLM 呼び出しのため）。
AI Scientist は v1/v2 とも `vertex_ai/` prefix で `AnthropicVertex` に振り分ける分岐を持つため、Vertex 経由（GCP 課金）と Console 従量課金のどちらでも動く。Vertex を使う場合、Model Garden のモデル利用申請に24〜48時間かかることがあるので早めに通しておく。なお `AVAILABLE_LLMS` のモデル一覧は Claude 3 系で止まっているため追記が必要。
